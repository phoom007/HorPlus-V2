# HorPlus-V2 — แผนพัฒนาฝั่งผู้เช่าให้พร้อม production (Tenant Production Backlog)

เอกสารนี้เป็นรายการงาน (การ์ด) ให้ agent พัฒนาฝั่งผู้เช่าจนใช้งานได้จริงทุกฟีเจอร์ และทดสอบจริงบน https://app.hor-plus.com ด้วยบัญชี LINE ที่ผูกกับผู้เช่าในฐานข้อมูลอยู่แล้ว ผ่าน LIFF ของผู้เช่า https://liff.line.me/2011672957-pIlWUt9e

## 0. วิธีใช้ไฟล์นี้ (สำหรับ agent)

- เริ่มงานด้วย `/horplus-tenant` (ไฟล์ `.agents/workflows/horplus-tenant.md`) workflow นี้จะเลือกการ์ดแล้วส่งต่อให้ `/horplus-task`
- อ่านหัวข้อ 0–5 ครั้งเดียวต่อบทสนทนา จากนั้นอ่านเฉพาะการ์ดที่กำลังทำ ไม่ต้องโหลดการ์ดอื่น
- 1 การ์ด = 1 task file = 1 commit ถ้าการ์ดต้องแก้เกิน 15 ไฟล์ ให้แบ่งเป็น `<การ์ด>a`, `<การ์ด>b` แล้วบอก PO
- "ปัญหาตอนนี้" ในแต่ละการ์ดตรวจจากโค้ดเมื่อ 2026-09-24 เลขบรรทัดอาจเลื่อน ให้ค้นจากชื่อ route หรือฟังก์ชัน และต้องเปิดโค้ดจริงใน Step 2 ของ `/horplus-task` ทุกครั้ง ห้ามเชื่อเลขบรรทัดในไฟล์นี้โดยไม่ตรวจ
- "AC ขั้นต่ำ" เพิ่มได้ ห้ามตัด ถ้า AC ข้อไหนขัดกับการตัดสินใจของ PO ให้ถาม PO
- "ต้องยืนยันกับ PO ก่อนเริ่ม" ถ้ายังไม่มีคำตอบในหัวข้อ 14 ให้ถาม PO ครั้งเดียวรวมทุกข้อของการ์ดนั้น พร้อมข้อเสนอ แล้วทำส่วนที่ไม่ขึ้นกับคำตอบไปก่อน (core rules 4a) ข้อเสนอในไฟล์นี้ยังไม่ใช่คำตอบของ PO ห้ามใช้แทนคำตอบ

## 1. เป้าหมายและขอบเขต

เป้าหมาย: ผู้เช่าใช้งานผ่าน LINE OA/LIFF ได้ครบทุกฟีเจอร์ ข้อมูลถูกต้อง ปลอดภัย และพร้อมเปิดใช้จริง

ขอบเขตตาม PT-1 คือฟีเจอร์ 4 กลุ่ม (R, B, C, P) บวกงานที่ต้องทำก่อนและหลัง (S, L, Z):

| กลุ่ม | การ์ด |
|---|---|
| ความปลอดภัยพื้นฐานของฝั่งผู้เช่า (ทำก่อน) | S1–S7 |
| ลงทะเบียน, claim, อนุมัติ, เข้าพอร์ทัล | R1–R4 (และ S5, S6) |
| บิล, ชำระเงิน, SlipOK, ใบเสร็จ | B1–B5 |
| สัญญา, ต่อสัญญา, ย้ายออก, หมดสัญญา | C1–C4 |
| โปรไฟล์, ผู้พักร่วม, แจ้งซ่อม, ประกาศ, การแจ้งเตือนในแอป | P1–P3 |
| ข้อความ LINE และจำนวนการส่งข้อความ | L1–L4 |
| ตรวจรวมก่อน production | Z1 |

นอกขอบเขต: ฝั่งเจ้าของหอที่ไม่เกี่ยวกับผู้เช่า, แพ็กเกจ/การชำระค่าแพ็กเกจของ HorPlus, หน้า Admin HorPlus

## 2. การตัดสินใจของ PO

ลำดับน้ำหนัก: คำสั่งของ PO ในบทสนทนา → ตารางในหัวข้อนี้และคำตอบในหัวข้อ 14 → `docs/REQUIREMENTS-LOCK.md` (ย่อว่า REQ) → เอกสารอื่น → โค้ด (แค่พฤติกรรมปัจจุบัน)

การตัดสินใจจาก `docs/uat/e2e-journeys/00-README.md` ที่ใช้กับงานนี้ (PO-1, PO-3, PO-7, PO-8, PO-9 ใช้กับการทดสอบ E2E เท่านั้น ไม่ใช้ที่นี่):

| รหัส | สรุป |
|---|---|
| PO-2 | จำลองเวลาโดยตั้งวันผ่านหน้าจอปกติเท่านั้น ห้ามแก้ฐานข้อมูล |
| PO-4 | สลิปผู้เช่าต้องตรวจด้วย SlipOK เจ้าของ/ผู้จัดการ override ได้ แต่ต้องใส่เหตุผลทุกครั้ง |
| PO-5 | บิลออก, ยืนยัน/ปฏิเสธการชำระ, แจ้งซ่อม และประกาศ ต้องส่งทาง LINE ด้วย |
| PO-6 | จำนวนการส่งข้อความที่แสดง = โควตาแพ็กเกจ − จำนวนที่ LINE OA ใช้ไปจริงเดือนนี้ (อ่านจาก LINE นับทุกข้อความของ OA) และหยุดส่งที่ตัวเลขเดียวกัน |
| PO-10 | บิล 3 แบบ ดูข้อความของ PO ด้านล่าง |
| PO-11 | ผู้เช่าแจ้งย้ายออกเองจากพอร์ทัลได้ |
| PO-12 | ถึงวันสิ้นสุดสัญญาโดยไม่ต่อ: สัญญายังค้างจนเจ้าของทำเรื่องย้ายออก บิลค่าเช่าหยุดหลังวันสิ้นสุด เจ้าของเห็นคำเตือน "หมดอายุ" |

ข้อความของ PO เรื่องบิล (PO-10):

> "บิลมี 3 แบบ ได้แก่ บิลรายเดือน (ค่าน้ำค่าไฟ) = แสดงให้ผู้เช่าเหมือนในหน้าจดมิเตอร์ถ้า สถานะ = รอชำระ , บิลค่าเช่า = แสดงรอบที่ 1.ตอนลงทะเบียนผู้เช่าแล้ว ถ้าค่าเช่า > 0 ก็แสดงเป็นทันที 2.แสดงทุกต้นเดือน วันที่ 1 ตามที่ยังชำระไม่ครบ , บิลประกัน/มัดจำ = แสดงตอนเจ้าของหอพักอนุมัติแล้ว แสดงขึ้นมาเลย ถ้ายังไม่ชำระ รอบเดียวของผู้เช่าคนนั้น"

การตัดสินใจเพิ่มสำหรับงานฝั่งผู้เช่า:

| รหัส | การตัดสินใจ |
|---|---|
| PT-1 | ทำครบ 4 กลุ่ม: ลงทะเบียน/claim, บิล/ชำระเงิน, สัญญา/ต่อสัญญา/ย้ายออก, โปรไฟล์/แจ้งซ่อม/ประกาศ/การแจ้งเตือน |
| PT-2 | ปิดช่องโหว่ความปลอดภัยก่อน แล้วค่อยทำฟีเจอร์ (ลำดับการ์ดในหัวข้อ 5) |
| PT-3 | ทดสอบกับหอที่มีอยู่แล้วในฐานข้อมูลของ pilot และบัญชี LINE ที่ผูกกับผู้เช่าไว้แล้ว เปิดผ่าน https://liff.line.me/2011672957-pIlWUt9e |
| PT-4 | สลิปผู้เช่าตรวจด้วยบัญชี SlipOK กลางของ HorPlus |

จุดที่ REQ เขียนต่างจาก PO หรือจากแผนนี้:

- REQ §7 (บรรทัด 139–140) ให้บิลเป็น `DRAFT` แล้วรอกด `ISSUE` แต่ PO-10 ให้บิลค่าเช่าและบิลมัดจำแสดงต่อผู้เช่าทันทีตามเงื่อนไข ส่วนบิลค่าน้ำค่าไฟแสดงเมื่อสถานะเป็น "รอชำระ" ตามหน้าจดมิเตอร์ → ใช้ PO-10
- REQ §9 (บรรทัด 164) นับเฉพาะ push ที่ HorPlus ส่งสำเร็จ แต่ PO-6 ให้แสดงตามจำนวนที่ LINE OA ใช้ไปจริง → ใช้ PO-6
- REQ §5 (บรรทัด 111) ปุ่มลงทะเบียน "ไม่ใช่ token เฉพาะคน" แต่ S2 เสนอให้ปุ่มถาวรสร้างลิงก์ใช้ครั้งเดียวเพื่อยืนยันตัวตน → ต้องให้ PO ยืนยันใน S2

## 3. สภาพแวดล้อมทดสอบ (หอที่มีอยู่ + LINE ที่ผูกแล้ว + LIFF)

### 3.1 ผู้เช่าเข้าระบบอย่างไรตอนนี้ (ข้อเท็จจริงจากโค้ด)

1. ผู้เช่ากดปุ่ม "ลงทะเบียนผู้เช่า" ใน rich menu ของ OA หอ หรือพิมพ์ "ลงทะเบียน"/"จองห้อง" หรือเพิ่มเพื่อน → webhook สร้างลิงก์เชิญ อายุ 7 วัน (`server/src/services/line-oa.service.ts:2121`, `:2156-2157`, `:2268-2273`; `server/src/services/tenant-registration-invite.service.ts:13-14`)
2. OA ตอบเป็น Flex (`line-oa.service.ts:135`) ที่มีปุ่มเปิด `https://liff.line.me/2011672957-pIlWUt9e?t=<token>` (สร้าง URL ที่ `:125-133`)
3. หน้าเว็บเปลี่ยนเส้นทางไป `/api/v1/auth/line-tenant-entry?t=<token>` (`src/App.tsx:108-118`, `:154-159`) server ตรวจ token แล้วสร้าง session แบบ cookie และส่งไป `/tenant` (`server/src/routes/auth.routes.ts:787-1042`) หลังจากนี้ช่อง URL จะไม่มี `?t=` แล้ว
4. หน้าเว็บไม่ส่ง LIFF ID token หรือ access token ให้ server และ server ไม่ได้ตรวจตัวตน LINE กับ LINE (ต่างจาก `docs/production-blueprint/adr/ADR-003-authentication-and-session.md:16` และ `docs/security/SECURITY-CONTRACTS.md:69-70`) → แก้ใน S2
5. ลิงก์ `?t=` ใช้ซ้ำได้ใน 7 วันจาก browser ใดก็ได้ จะถูกใช้หมดเฉพาะตอนส่งคำขอลงทะเบียนหรือ claim (`server/src/services/tenant-registration.service.ts:211`, `:2714`) ผู้เช่าที่ผูกแล้วจึงใช้ลิงก์เดิมได้ 7 วัน และใครได้ลิงก์ไปก็เข้าเป็นผู้เช่าคนนั้นได้ → แก้ใน S2
6. session ของ LINE มี user id แบบ `ag_user_<grantId>` (`server/src/services/auth.service.ts:300`) ไม่ใช่ uuid
7. ผู้เช่าที่ผูกแล้วยังได้ rich menu ตัวเริ่มต้น (ปุ่ม "ลงทะเบียนผู้เช่า" และ "คู่มือ") เพราะ `linkActiveTenantRichMenu` (`server/src/services/line-richmenu.service.ts:430`) ไม่มีผู้เรียก ตอนนี้ผู้เช่าจึงเข้าพอร์ทัลด้วยการกด "ลงทะเบียนผู้เช่า" → แก้ใน R1
8. หนึ่งบัญชี LINE มี grant ACTIVE ได้ 1 role ต่อหอ (REQ §3 บรรทัด 79; unique index ใน `server/prisma/migrations/20260913140000_make_access_grant_line_friend_id_nullable/migration.sql`)

### 3.5 SQL สำรวจผู้เช่าที่ผูก LINE แล้ว (อ่านอย่างเดียว)

ตาราง `dormitory_line_friends`, `dormitory_access_grants`, `dormitory_line_configs` เปิด RLS ไว้ ถ้าผลว่าง ให้ถาม PO ว่าใช้ role ไหนอ่าน

```sql
BEGIN TRANSACTION READ ONLY;
SELECT d.id AS dormitory_id, d.name AS dormitory_name,
       t.id AS tenant_id, t.tenant_number, t.display_name AS tenant_display_name,
       t.status AS tenant_status,
       COALESCE(rc.room_number, ro.room_number) AS room_number, kc.status AS contract_status,
       (t.line_friend_id IS NOT NULL) AS line_friend_bound,
       f.display_name AS line_display_name, f."friendStatus" AS line_friend_status,
       EXISTS (SELECT 1 FROM dormitory_access_grants g
               WHERE g.dormitory_id = t.dormitory_id AND g.line_friend_id = t.line_friend_id
                 AND g.status = 'ACTIVE' AND g.role_code = 'TENANT') AS has_active_tenant_grant,
       (SELECT string_agg(DISTINCT g.role_code, ',') FROM dormitory_access_grants g
         WHERE g.dormitory_id = t.dormitory_id AND g.line_friend_id = t.line_friend_id
           AND g.status = 'ACTIVE') AS active_grant_roles,
       COALESCE(c.is_connected, false) AS line_config_connected,
       COALESCE(c.webhook_active, false) AS line_webhook_active
FROM tenants t
JOIN dormitories d ON d.id = t.dormitory_id AND d.deleted_at IS NULL
LEFT JOIN dormitory_line_friends f ON f.id = t.line_friend_id
LEFT JOIN dormitory_line_configs c ON c.dormitory_id = t.dormitory_id
LEFT JOIN LATERAL (SELECT k.status, k.room_id FROM contracts k
                   WHERE k.tenant_id = t.id AND k.deleted_at IS NULL
                     AND k.status IN ('active','approved_scheduled','expiring_soon','waiting_extension')
                   ORDER BY k.start_date DESC LIMIT 1) kc ON true
LEFT JOIN rooms rc ON rc.id = kc.room_id
LEFT JOIN LATERAL (SELECT o.room_id FROM occupancies o
                   WHERE o.tenant_id = t.id AND o.status = 'ACTIVE'
                   ORDER BY o.started_at DESC LIMIT 1) oc ON kc.room_id IS NULL
LEFT JOIN rooms ro ON ro.id = oc.room_id
WHERE t.deleted_at IS NULL
ORDER BY d.name, room_number NULLS LAST, t.display_name;
ROLLBACK;
```

ผู้เช่าที่ใช้เป็น TA/TB ได้ต้องมี `tenant_status = active`, `line_friend_bound = true`, `has_active_tenant_grant = true`, `active_grant_roles = TENANT` และหอมี `line_config_connected = true`

## 4. กติกาเพิ่มสำหรับการ์ดฝั่งผู้เช่า

ใช้ core rules และ `/horplus-task` ตามปกติ บวกกติกานี้:

1. การทดสอบเน้นมุมมอง D (บนคอมพิวเตอร์ในกรอบขนาดจอมือถือจริง Mobile Viewport) เป็นหลักตามคำสั่ง PO เนื่องจากขนาดกรอบแสดงผลเหมือนกันและ Agent สามารถตรวจสอบ UI, ปุ่ม, Toast, Network API และ Database ได้ครบถ้วนในตัว ไม่ต้องให้ PO คอยทดสอบ M ทุกรอบ
2. การ์ดที่เกี่ยวกับสิทธิ์ เงิน หรือการแยกข้อมูล ต้องมี AC ที่ "ต้องถูกปฏิเสธ" และตรวจผ่าน live API บน app.hor-plus.com ด้วย session ของผู้ใช้จริง (ไม่ใช่ mock)
3. หลัง deploy ครั้งสุดท้ายของการ์ด ให้รัน regression สั้น 6 ข้อ: แบบ D ด้วย TA เข้าหน้าแรก, ดูบิล, ดูสัญญา, ดูประกาศ, ดูโปรไฟล์ และแบบ OW เปิดหน้ารายชื่อผู้เช่า จดผลใน task file
4. AC ที่ต้องรอเวลาจริง (วันที่ 1, วันสิ้นสุดสัญญา, job รายชั่วโมงเกิน 60 นาที) หรือรอการ์ดอื่น: บันทึกเป็น `NOT RUN (ตรวจภายหลัง: <วันที่หรือการ์ด>)` ขอ PO อนุมัติการข้าม แล้วจดคำอนุมัติใน task file ก่อนรายงาน ห้ามแก้ข้อมูลในฐานข้อมูลเพื่อเร่งเวลา
5. ประสิทธิภาพ: route ใหม่หรือที่แก้ต้องมีขอบเขตข้อมูล (ต่อผู้เช่า/สัญญา) และจำกัดจำนวนรายการ หน้าแรกของผู้เช่าไม่เรียก API ซ้ำซ้อน
6. ตารางในหัวข้อ 5: ตอนเริ่มการ์ดแก้สถานะเป็น IN PROGRESS ในไฟล์ (ยังไม่ต้อง commit) ตอนถึง READY FOR UAT แก้สถานะและ task id แล้ว commit ไฟล์นี้รวมกับงานของการ์ด ส่วน commit hash และสถานะ ACCEPTED ให้เติมใน commit ของการ์ดถัดไป ห้าม amend ห้าม commit เพิ่ม
7. คำตอบของ PO ที่ได้ระหว่างทำการ์ด จดลงหัวข้อ 14 คำต่อคำ เพื่อให้การ์ดอื่นใช้ต่อ
8. การทดสอบการกรอกข้อมูล (เช่น ลงทะเบียนผู้เช่า): ต้องกรอกข้อมูลครบทุกช่องที่มีให้กรอกจริง (Full Comprehensive Data) และใส่หลายรายการ เช่น ยานพาหนะหลายคัน (รถยนต์+มอเตอร์ไซค์ ระบุยี่ห้อและทะเบียน), สัตว์เลี้ยง (ประเภท ชื่อ จำนวน), ผู้พักร่วมหลายคน, ผู้ติดต่อฉุกเฉิน, รูปบัตร และลายเซ็น พร้อมตรวจสอบการแสดงผลครบทุกจุด (ฐานข้อมูล, หน้าเจ้าของหอ, และหน้าโปรไฟล์ผู้เช่า)

## 7. Phase S — ปิดช่องโหว่ความปลอดภัยฝั่งผู้เช่า (ทำก่อน)

ทุกการ์ดใน Phase S เป็นงานเสี่ยง ต้องผ่าน Gate A ก่อนเขียนโค้ด (core rules 6)
คำย่อในคอลัมน์ "ตรวจที่": D = browser ของ agent บน app.hor-plus.com ในนามผู้เช่า, M = PO บนมือถือผ่าน LIFF, API = เรียก live API บน app.hor-plus.com ด้วย session จริง, OW = owner/manager/staff web, DB = SELECT อ่านอย่างเดียว

### S1 — ตัวตนผู้เช่ามีทางเดียว: ปิด fallback และผู้เช่าปลอม [สถานะ: READY FOR UAT]

ที่มา: REQ §10 (บรรทัด 171: ทุกคำสั่งต้อง derive หอ/role จาก session หรือ verified LINE identity), REQ §3 (บรรทัด 79: หนึ่ง user หนึ่งบทบาทต่อหอ), REQ §5 (บรรทัด 121), ADR-003:16
ปัญหาตอนนี้:
- fallback ของพอร์ทัล: ถ้าไม่มี cookie `horplus_session` ที่ใช้ได้ จะเลือกหอจาก cookie/header/query หรือ id ที่ hardcode ไว้ แล้วใช้ grant ACTIVE ที่อัปเดตล่าสุดของ role ใดก็ได้ในหอนั้น (`server/src/routes/tenant-portal.routes.ts:441-527`, hardcode `:472`, เลือก grant `:475-479`) ตอนนี้ `requireSession` กันไว้ก่อน (`server/src/routes/index.ts:158`, `:200`) แต่จะเปิดทันทีถ้า `SESSION_COOKIE_NAME` ไม่ใช่ `horplus_session`
- `resolveTenantContext` ยอมรับ membership ทุกสถานะและทุก role และหยิบ membership แรกโดยไม่สน `x-dormitory-id` (`tenant-portal.routes.ts:41-56`)
- header `x-registration-id` ผูก `line_friend_id` ของ session ใดก็ได้เข้ากับผู้เช่าที่อนุมัติแล้ว (`tenant-portal.routes.ts:132-170`, `:197-240`)
- ทางเข้าผู้เช่านำ grant ACTIVE ของ role ใดก็ได้มาใช้ บัญชี LINE ของเจ้าของ/พนักงานที่กด "ลงทะเบียนผู้เช่า" จะได้ session ของ role นั้นในหน้าผู้เช่า (`server/src/routes/auth.routes.ts:907-915`)
- หน้าเว็บสร้างผู้เช่าปลอมเมื่อโหลดโปรไฟล์ไม่ได้ (`src/router/guards.tsx:137-163` ใช้ที่ `:180`, `:184`) ทำให้หน้า "ไม่มี session" (`:193-229`) ไม่เคยแสดง และ `src/pages/tenant/TenantRegisterPage.tsx:37`, `:108` hardcode id หอ, `:50` hardcode ชื่อหอ
- route ที่ผู้เช่าใช้นอก `tenant-portal` หาผู้เช่าจาก `linkedUserId = auth.userId` (`server/src/routes/payment.routes.ts:111`, `:876`, `:908`; `server/src/routes/receipt.routes.ts:22`) แต่ session ของ LINE มี userId `ag_user_...` (`server/src/services/auth.service.ts:300`) ส่วน `linked_user_id` เป็น uuid Prisma จึง error ผลคือผู้เช่าที่เข้าผ่าน LINE ส่งสลิปและเปิดใบเสร็จไม่ได้
ผลที่ต้องได้:
- มีตัวหาผู้เช่าจาก session ตัวเดียว ใช้ทุก route ที่ผู้เช่าเรียก: session → grant ที่ ACTIVE และเป็น TENANT ของหอนั้น → line friend → ผู้เช่าที่ active
- ไม่มี fallback, ไม่มี id หอหรือชื่อหอ hardcode, ไม่มีการผูกผ่าน header, ไม่มีผู้เช่าปลอม
- ไม่มี session → หน้าเว็บแสดงข้อความภาษาไทยให้เปิดจากเมนูใน LINE OA ของหอ

### S2 — ยืนยันตัวตน LINE ฝั่ง server (LIFF ID token) และลิงก์เชิญ [สถานะ: READY FOR UAT]

ที่มา: REQ §10 (บรรทัด 171), ADR-003:16 (ตรวจ issuer/audience/nonce/replay), `docs/security/SECURITY-CONTRACTS.md:69-70`, REQ §5 (บรรทัด 110–111: เข้าผ่านปุ่มถาวรใน LINE OA/LIFF, ปุ่มใช้ได้จนเจ้าของปิดรับ)
ปัญหาตอนนี้:
- ไม่มีการตรวจ LIFF token กับ LINE ที่ใดเลย หน้าเว็บไม่เรียก `liff.getIDToken()`/`liff.login()` (`src/utils/liff.ts`; `getLiffProfile` ที่ `:65` ไม่มีผู้เรียก)
- ลิงก์ `?t=` คือกุญแจเข้าบัญชี (หัวข้อ 3.1 ข้อ 5)
- `PREFER_DIRECT_LINE_ENTRY=true` ส่งลิงก์ตรงไป `line-tenant-entry` โดยไม่ผ่าน LIFF (`server/src/services/line-oa.service.ts:128`, `:132`)
- LIFF ID ของผู้เช่าถูก hardcode (`src/utils/liff.ts:22`, `line-oa.service.ts:113`, `server/src/services/line-richmenu.service.ts:252`) ขัดกับ core rules ข้อ 8
- userId ของ LINE แยกตาม provider ถ้า OA ของหออยู่คนละ provider กับ channel ของ LIFF userId จะไม่ตรงกัน จับคู่ตรง ๆ ไม่ได้ ต้องใช้ลิงก์จาก OA เป็นตัวเชื่อมครั้งแรก
ผลที่ต้องได้ (เป็นข้อเสนอ ต้องให้ PO ยืนยันข้อที่ระบุด้านล่าง):
- หน้าเว็บส่ง LIFF ID token ให้ server ทุกครั้งที่สร้าง session server ตรวจกับ LINE (channel ID ของ LIFF จาก env) และตรวจ audience/expiry/nonce ตาม ADR-003
- ครั้งแรก: ผู้ใช้กดปุ่มจาก OA ของหอ → ลิงก์ที่ปุ่มสร้าง (ใช้ครั้งเดียว อายุสั้น) + ID token ที่ตรวจแล้ว → จับคู่ตัวตน LIFF กับ line friend ของหอ แล้วลิงก์นั้นใช้ไม่ได้อีก
- ครั้งต่อไป: ID token ที่ตรวจแล้วอย่างเดียวพอ ลิงก์อย่างเดียวสร้าง session ไม่ได้อีก
- เปิดนอกแอป LINE → `liff.login()` พาไป LINE Login แล้วกลับมาพอร์ทัล
- LIFF ID และ channel ID ของผู้เช่ามาจาก config
- ถ้าต้องเพิ่มตาราง/คอลัมน์: backup ก่อน migrate (core rules 7)

### S3 — ผู้เช่าเห็นเฉพาะข้อมูลของตัวเอง

ที่มา: REQ §8 (บรรทัด 156: ผู้เช่าเดิมไม่เข้าดูเอกสารย้อนหลัง, 158: ผู้เช่าใหม่เห็นเฉพาะข้อมูลของตน), REQ §10 (บรรทัด 172)
ปัญหาตอนนี้:
- บิล, การชำระ, ใบเสร็จ ดึงด้วย tenantId หรือ roomId หรือ contractIds โดยไม่จำกัดช่วงเวลา ผู้เช่าใหม่จึงเห็นของผู้เช่าเก่าในห้องเดียวกัน (`server/src/routes/tenant-portal.routes.ts:358-364`, `:1616-1624`, `:1668-1673`) ส่วนหน้ารายละเอียดบิลใช้เฉพาะ tenant/contract (`:384-428`) ไม่ตรงกับรายการ
- ค่าน้ำค่าไฟดึงตามห้อง ตั้งแต่วันเริ่มสัญญาแรกไม่มีขอบบน (`:791-808`)
- ผู้เช่าที่พบจาก `linkedUserId` ไม่กรองสถานะ ผู้เช่าเก่ายังเห็นบิลและสัญญาเดิม (`:69-72`)
- QR และตัวเลือกการชำระรับ `?amount=` และ bill id หลายใบจาก client โดยไม่ตรวจว่าเป็นของผู้เช่าคนนี้ (`:1442-1450`, `:1496-1511`)
- `GET /rooms` หา registration โดยไม่จำกัดหอ ทำให้ข้อมูลห้องและชื่อผู้เช่าข้ามหอได้ (`:579-636`)
ผลที่ต้องได้:
- ทุก endpoint ของผู้เช่ากรองด้วยสัญญาของผู้เช่าคนนี้และช่วงวันของสัญญานั้น รายการและรายละเอียดใช้กติกาเดียวกัน
- ยอดใน QR คำนวณที่ server จากบิลของผู้เช่าเท่านั้น
- รายการมีการจำกัดจำนวน/แบ่งหน้า

### S4 — ผู้เช่าเรียก API ของเจ้าของไม่ได้ และ CSRF ครบ

ที่มา: REQ §3 (ตารางสิทธิ์ บรรทัด 88–96), REQ §10 (บรรทัด 171), ADR-003 (cookie mutation ใช้ CSRF)
ปัญหาตอนนี้:

  - รองรับรูปแบบชื่อภาษาไทยที่หลากหลาย เช่น ตัด/แปลงคำนำหน้า (`นางสาว`, `น.ส.`, `นาย`, `นาง`, ช่องว่าง) และรองรับการย่อนามสกุล (เช่น ชื่อในระบบ "นางสาว ภูวนาท ทานาลาด" เทียบกับสลิป "ภูวนาท ท", "น.ส.ภูวนาท ท", "นางสาวภูวนาท", "ภูวนาท ทานาลาด") ให้ระบบฉลาดพอที่จะตรวจผ่านอย่างถูกต้อง ไม่ปฏิเสธผิดพลาด
- **การจัดการกรณีสลิปมีปัญหา และ Fallback Handling (B3):**
  - **1. สลิปไม่มี QR Code, QR Code ไม่ตรง หรือเป็นภาพหลักฐานการโอนที่ไม่ใช่สลิปธนาคารมาตรฐาน:**
    - ในหน้าชำระเงินของผู้เช่า เมื่อแนบรูปแล้วจะมีปุ่ม **"ยกเลิกส่งรูป"** เพื่อให้ผู้เช่ากดแล้วรูปจะหายไปจากเมนูการชำระเงินทันที เหมือนไม่เคยส่งรูปเข้าระบบมาก่อน
    - หากส่งเข้าระบบแล้วตรวจพบว่าไม่ใช่สลิปมาตรฐาน/ไม่พบ QR รายการจะเข้าสู่แท็บ **"สลิปผิดพลาด" (Tab 4 ในหน้าการชำระเงินของเจ้าของหอพัก)** เพื่อให้เจ้าของเปิดดูรูปหลักฐานและกด **"รับเงิน / ยืนยันการชำระ"** ได้ด้วยตนเอง (Manual Accept / Override)
  - **2. หากระบบ SlipOK โควตาหมด:**

  - **3. หากระบบ SlipOK ขัดข้อง/ล่ม:**
    - แจ้งข้อความภาษาไทยให้ผู้เช่าทราบและแนะนำให้ **"แนบใหม่"**
- เจ้าของ/ผู้จัดการเห็นผล SlipOK ในหน้าตรวจสลิป อนุมัติหรือปฏิเสธที่ต่างจากผล SlipOK ต้องกรอกเหตุผล และบันทึก audit
